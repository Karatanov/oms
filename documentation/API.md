# API Handover Reference

The API base is `/api/v1`; JSON is the default representation. `server/requests.http` contains development examples. There is no generated OpenAPI endpoint in Phase 1, so routes and DTOs in `server/src/main/kotlin/oms/ufsi` are the code-level source of truth.

## Authentication and errors

- **POST** `/auth/login`, **POST** `/auth/logout`, **POST** `/auth/activate`.
- Browser calls use the HTTP-only session cookie. Other clients may send `Authorization: Bearer <token>`.
- Errors use an HTTP status plus `{ "code": "...", "message": "..." }`. `400` is validation/parsing, `401` is unauthenticated or inactive, `403` is RBAC/project-scope denial, `404` is missing resource, and `409` is a state/conflict condition.

## Endpoint groups

Inspection report responses include optional `authorUsername`, resolved from the report creator. Clients may display an em dash if it is absent. This is an additive field; UUIDs and existing workflow/authorization contracts are unchanged.

- Health: **GET** `/health`, **GET** `/api/v1/health`.
- Dashboard/map: **GET** `/dashboard`, **GET** `/projects/map`.
- Projects: list/detail/create/update/delete, bulk status/reassignment, XLSX export and health/safety observations under `/projects`. Detail responses additionally expose nullable `programmeDetails` for the top-level URP III programme and nullable `monitoringDetails` for imported subprojects, including stable source IDs, bilingual names, responsible organisations, DREAM/application references, source statuses and provenance. Unknown location/classification fields are returned as clean empty display values; `/projects/map` omits records without real coordinates. Create/update accept designer and construction-contract details, including `designStartDate` and `designPlannedEndDate`; `designDurationDays` is returned as a calculated field and a planned design completion before its start is rejected. The same contract fields are available for technical supervision (`technicalSupervision*`) and engineer-consultant (`engineerConsultant*`) organisations; their duration fields are calculated in the response and their planned end dates are validated. Requests also accept a keyed `amounts` map (`budget`, `engineer`, `supervision`, `construction`). Each amount snapshot contains the exact decimal source amount, EUR/UAH currency, opposite-currency equivalent, UAH-per-EUR rate, rate date and manual-edit flag. **GET** `/exchange-rates/eur` returns today's official NBU EUR rate (or the latest preceding publication date) for Admin/Project Manager forms.
- Inspections/SIR: manual create, XLS/XLSX import, report edit/delete/move/submit/review, findings, photos and original source-file download/replacement. `POST /projects/{projectUuid}/inspection-reports/manual` fills the approved SIR workbook template rather than building a generic worksheet: column widths, merged cells, fonts, borders, row heights and print layout are preserved. The reference workbook's photo-attachment sheet is deliberately excluded from a manual report so it cannot carry photographs from another inspection. Uploaded photographs are then rendered on a generated `Photos` sheet in the downloadable manual XLSX, using only that report's own evidence. `PUT /inspection-reports/{reportUuid}/source-file` replaces a missing or incorrect XLS/XLSX source without creating a duplicate report. The edit window supports date, title/summary, planned/unplanned/final type, optional GPS coordinates, source-file replacement and photo upload. Its Project → Subproject → Subproject part selector invokes the dedicated move operation when the selected deepest level changes. The system does not fabricate SIR codes from UUIDs; a source code remains optional metadata only. Administrators and Project Managers may correct a workflow status from that edit window through `PATCH /inspection-reports/{reportUuid}/status`; Inspectors retain the normal submit-only workflow. Photos may be added to a completed report because they are inspection evidence received after the report workflow.
- Session restoration: `GET /auth/session` returns the current authenticated user from the HttpOnly `oms_session` cookie. The web client calls it silently after a browser refresh, preserving the signed-in workspace without storing a bearer token in browser storage.
- Project dates accept either manual `DD.MM.YYYY` keyboard entry or the adjacent calendar and are submitted as ISO `YYYY-MM-DD` values.
- Document types are limited to the persisted document taxonomy: Contract, Design, Estimate, Invoice, Act, Photo and Other. Project hierarchy placement is selected separately and is never written into `documents.doc_type`.
- Financials: CRUD, import and export under `/projects/{projectUuid}/financials`.
- Documents: list/upload/download/delete under `/projects/{projectUuid}/documents`.
- Procurement: list and Admin/PM mutations under `/procurements`. Imported records are linked to the owning OMS subproject and preserve source-backed procurement method, tender-document type, planned publication/submission/contract dates, comments and contract type in the database.
- Administration: Admin-only users CRUD and role lookup under `/users` and `/roles`.

List routes accept the filters/pagination implemented by their route DTO parsing; response metadata is represented by `PageMetadata`. Upload routes use multipart form data, validate size/type in their services, save bytes under `OMS_UPLOAD_DIR`, and persist metadata only after storage succeeds. Download performs authorization before resolving the stored file and returns controlled `404` for absent metadata or bytes.

Backend authorization is authoritative: Admin has full access; Project Manager mutates only assigned projects; Inspector writes SIR/photo content; Viewer is the authenticated read-only role. `POST /auth/guest` creates an anonymous browser session, not a user account or role; it is limited to the public map, project registry and general project-information endpoint. Financial and document mutations are Admin/PM only, and user administration is Admin only.
