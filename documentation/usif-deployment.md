# USIF and UR III deployments

The VPS and Render run the same Linux image published by `publish-ghcr.yml`. The existing VPS environment selects UR III by default. For USIF, the container entry point reads the server-side profile under `deploy/brands/usif`, renders the shared login and workspace pages into a private temporary web root and starts Ktor. The browser reads only the active profile's name. The login form, guest flow, API client and Compose workspace remain shared. GitHub Pages continues to use the existing UR III default.

## Provision the existing Render service

The existing service `oms` at `https://oms-3j46.onrender.com` runs the image-backed Free instance. The verified initial image revision is `85eeffe9b098`. The temporary test registry contains one TVET II parent and seven subprojects.

1. The existing TiDB Cloud cluster hosts the independent `oms_usif` catalog. Its application account can access only this catalog and system metadata. Use a MySQL JDBC URL with `sslMode=VERIFY_IDENTITY` and `DATABASE_DIALECT=mysql` for the tested isolated V80 schema. Keep the cluster's existing free quota and monitor it separately from Render.
2. The Free service uses temporary local storage under `/tmp/usif-uploads`. Files written through DurableFileStorage are mirrored into this database. Treat other local files as ephemeral. The small test workload has no paid disk.
3. The existing service pulls the exact GHCR image with workspace registry credential `github-ghcr`. Automatic source deploys are disabled. Scope the GitHub environment hook to this service.

4. Set the following service variables and restrict access to the service environment. Generate a unique random JWT secret of at least 32 characters. Set an explicit JDBC URL including the database name and the appropriate TLS trust settings for your provider.

| Render variable | Value or source |
|---|---|
| `OMS_BRAND` | `usif` |
| `OMS_PUBLIC_BASE_URL`, `CORS_ALLOWED_HOST` | `https://oms-3j46.onrender.com` |
| `DATABASE_URL`, `DATABASE_USER`, `DATABASE_PASSWORD`, `OMS_JWT_SECRET` | Private USIF service environment |
| `DATABASE_DIALECT` | `mysql` |
| `OMS_WEB_DIR` | `/opt/oms/web` |
| `OMS_UPLOAD_DIR` | `/tmp/usif-uploads` |
| `PROCUREMENT_AUTO_REFRESH_ENABLED`, `SUBPROJECT_AUTO_REFRESH_ENABLED`, `PAYMENT_MONITORING_AUTO_REFRESH_ENABLED` | `false` |
| `OMS_IMPORT_PARENT_SITE_NUMBER` | Optional. Unique site number of the organization's parent project when enabling manual registry imports |

5. Configure the GitHub Environment `usif` with deployment branch `master` and its own `RENDER_DEPLOY_HOOK_URL` secret for this service. The existing `production` environment uses `VPS_SSH_PRIVATE_KEY` and `VPS_SSH_KNOWN_HOSTS`. GHCR publication uses the per-run `GITHUB_TOKEN`.
6. The first verified release creates 18 application tables and five roles. Confirm zero rows in every application table except `roles` before setup. From a trusted interactive terminal with the USIF environment and deployed server libraries run `java -cp '/opt/oms/lib/*' oms.urp3.config.BootstrapAdminKt` once. It prompts privately for a password and checks the user registry in a transaction. Normal startup does not create users.
7. Verify the public `/health`, `/ready`, `/version` and login page, both languages, login, guest access, and the empty registries. Verify the database identity separately from HTTP liveness.

## Schema and import policy

The V80 isolated migration contains MySQL DDL generated by applying the unchanged V1–V80 migrations to a disposable local MySQL 8 instance. The DDL preserves indexes, constraints and defaults. Auto-increment counters were reset and only the five roles were exported. The application runs Flyway normally from either the organization's legacy location or the isolated V80 location plus `db/common`. An empty USIF database records V80 as an executed migration. A subsequent release resolves that history and applies later versions. Existing nonempty databases without Flyway history are refused by Flyway. An interrupted DDL bootstrap requires inspection of the isolated database before recovery.

Start shared schema migrations at V81 in `server/src/main/resources/db/common`. Keep these compatible with the supported MySQL and TiDB deployments. Keep UR3-specific business imports in its own location or service and give every migration a unique increasing version. Preserve applied files and checksums.

The UR III procurement, subproject and payment jobs, bundled payment snapshot fallback, Google Drive OAuth imports and feedback spreadsheet are disabled in USIF. USIF keeps same-origin API, credentialed cookies, its own signing key and manual workbook uploads. Neutral services such as map tiles, geocoding and currency rates remain shared application features. Credentials for the UR III integrations belong only to UR III.

## Updates and rollback

After an approved merge to master the frontend is compiled, the combined image is published, and each deployment uses the SHA tag. The VPS retains its existing regression gates, SSH and rollback steps. The Render job waits for the image isolation test and regression gates. Pull requests run checks without releasing either site. A Render failure reports a separate failed job and does not roll back the VPS.

For a USIF rollback, choose the previous verified SHA from the Render deploy history and GitHub release run. With the USIF hook injected from the secret store, run `bash deploy/render/deploy.sh <previous-full-sha>`. It checks the revision, readiness, health and the USIF login page. For UR III use the existing VPS procedure from its deployment directory, `bash deploy.sh sha-<previous-full-sha> <previous-full-sha>`, with the existing registry authentication. The VPS script also restores the prior image after a failed rollout. Image rollback preserves database and file volumes. Confirm schema compatibility with the older application first. Database restoration is a separate recovery decision.
